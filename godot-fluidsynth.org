* Godot Fluidsynth
This plugin exposes [[https://www.fluidsynth.org/][FluidSynth]] to the Godot gaming engine by means of [[https://docs.godotengine.org/en/stable/tutorials/scripting/gdextension/what_is_gdextension.html][GDExtension]]. It was developed to provide realtime MIDI playback performance, and complement Godot's built-in MIDI input event handling and other excellent addons written in GDScript.

** Usage
Build prerequisites and commands live in the [[https://github.com/Tremolo-Labs/godot-fluidsynth#readme][README]].

*** Playing a MIDI file
#+begin_src gdscript
var player := GDMidiAudioStreamPlayer.new()
add_child(player)
player.set_soundfont("res://FluidR3_GM.sf2")
player.set_midi_file("res://song.mid")
player.fluidsynth_play()

# Or drive the synth directly:
player.program_select(0, 0, 0)
player.note_on(0, 60, 127)    # middle C, full velocity
player.pitch_bend(0, 8192)    # 14-bit value, 8192 = centered
player.note_off(0, 60)
#+end_src

Paths passed to the player resolve through Godot's resource system, so imported assets work as-is.

** Design
By default, Fluidsynth expects to be the audio driver looking for regular filesystem files. Godot packs assets into its own export file, so they're managed by Godot's ~Resource~ API and not visible to the filesystem. Godot is also the Audio driver. For this situation, Fluidsynth supports [[https://www.fluidsynth.org/wiki/api/audio-rendering/][custom rendering]], [[https://www.fluidsynth.org/wiki/api/soundfont-loader/][custom soundfont loaders]], and [[https://www.fluidsynth.org/wiki/api/midi-player/#fluid_player_add_mem][setting its player's MIDI data in-memory]]. To implement this, three classes are registered with the engine, and a small GDScript addon teaches Godot's importer about MIDI assets:

- ~GDMidiAudioStreamPlayer~ :: An ~AudioStreamPlayer~ subclass that synthesizes a Standard MIDI File through FluidSynth in realtime, pushing rendered stereo frames into the audio stream each frame with an ~AudioStreamGeneratorPlayback~.
- ~MidiFileReader~ :: A ~Resource~ holding raw ~.mid~ bytes (~PackedByteArray~) so MIDI data can travel inside Godot's resource system.
- ~SoundFontFileReader~ :: A ~Resource~ holding raw ~.sf2~ bytes, likewise.
- ~addons/midi/~ :: Import/save/load plugins converting ~.mid~ → ~.midstr~ and ~.sf2~ → ~.sf2str~.


*** Loading SoundFonts at runtime
The ~GDMidiAudioStreamPlayer~ initialization creates a custom soundfont loader that reads the raw bytes from Godot's ~Resource~ system, which has taken over the job of managing the files so that they can be bundled in the exported game.

But FluidSynth's built-in loader gets called first, and it wants a real path on disk. Since version 2.6 it stats the sfload path while building its sample cache and throws an exception when the in-memory pseudo-path cannot be found. As a workaround, we create a uniquely-named temp file under ~user://~, and delete it once ~fluid_synth_sfload~ has consumed it.

Issue [[https://github.com/Tremolo-Labs/godot-fluidsynth/issues/24][#24]] tracks filing this upstream so the in-memory loader can return; its legacy callbacks still sit unused i [[file:src/godot_fluidsynth.cpp::void GDMidiAudioStreamPlayer::set_soundfont(String p_soundfont) {][src/godot_fluidsynth.cpp]]. In-memory custom loaders are supposed to be a supported workflow. It's an upstream bug.

#+begin_example cpp
void GDMidiAudioStreamPlayer::set_soundfont(String p_soundfont) {
	soundfont = p_soundfont;

	if (!ResourceLoader::get_singleton()->exists(soundfont)) {
		return;
	}
	Ref<SoundFontFileReader> soundfont_file = ResourceLoader::get_singleton()->load(soundfont);
	if (soundfont_file.is_null()) {
		return;
	}
	// FluidSynth >= 2.6 stats the sfload path for its sample cache; our encoded
	// memory pseudo-path makes std::filesystem throw and abort the process.
	// Write the SoundFont to a real file and let the default loader handle it.
	static int temp_counter = 0;
	String temp_path = OS::get_singleton()->get_user_data_dir()
			+ "/godot_fluidsynth_" + String::num_int64(OS::get_singleton()->get_process_id())
			+ "_" + String::num_int64(temp_counter++) + ".sf2";

	Ref<FileAccess> f = FileAccess::open(temp_path, FileAccess::WRITE);
	if (f.is_null()) {
		return;
	}
	f->store_buffer(soundfont_file->get_data());
	f->close();

	sfont_id = fluid_synth_sfload(synth, temp_path.utf8().get_data(), 1);

	DirAccess::remove_absolute(temp_path);
}
#+end_example

*** Handing MIDI data to the synthesizer
FluidSynth accepts raw song bytes directly through ~fluid_player_add_mem~, so a loaded ~MidiFileReader~ feeds the player straight from memory.

#+begin_example cpp
void GDMidiAudioStreamPlayer::fluidsynth_play() {
	if (!ResourceLoader::get_singleton()->exists(midi_file)) {
		return;
	}
	Ref<MidiFileReader> midi = ResourceLoader::get_singleton()->load(midi_file);
	if (midi.is_null()) {
		return;
	}
	PackedByteArray byte_array = midi->get_data();

	if (byte_array.size() > 0) {
		fluid_player_add_mem(player, byte_array.ptr(), byte_array.size());
	}

	fluid_player_play(player);
	fluidsynth_playing = true;
}
#+end_example

*** Rendering pipeline
The ~GDMidiAudioStreamPlayer~ uses an ~AudioStreamGeneratorPlayback~ to fill its playback buffer at each ~~_process~ call. Every frame the node drains the synthesizer by hand. ~_process~ also doubles as the lifecycle watchdog: when FluidSynth reports the song finished, the player object is torn down and a fresh one replaces it lazily.

#+begin_example cpp
void GDMidiAudioStreamPlayer::_process(double delta) {
	if (player && fluid_player_get_status(player) == FLUID_PLAYER_DONE && fluidsynth_playing) {
		fluid_player_stop(player);
		fluid_player_join(player);
		delete_fluid_player(player);
		fluidsynth_playing = false;

		player = new_fluid_player(synth);
	}

	if (!synth || !player) {
		return;
	}

	if (is_playing() && !fluidsynth_playing) {
		fluidsynth_play();
	}

	if (is_playing()) {
		fill_buffer();
	}
}
#+end_example

~fill_buffer~ renders however many frames the stream can accept (capped at 44100 per pass) into an interleaved buffer, then walks it two floats at a time pushing stereo frames. Due to buffer format differences, ~AudioStreamGeneratorPlayback.push_frame~ is probably about the same cost as ~AudioStreamGeneratorPlayback.push_buffer~ after building a ~PackedVector2Array~ out of the interleaved stereo buffer frames. We might revisit this.

#+begin_example cpp
void GDMidiAudioStreamPlayer::fill_buffer() {
	if (stream_playback.is_null() || !buffer || !synth) {
		return;
	}
	int64_t to_fill = stream_playback->get_frames_available();
	if (to_fill > 44100) {
		to_fill = 44100;
	}
	fluid_synth_write_float(synth, to_fill, buffer, 0, 2, buffer, 1, 2);
	int index = 0;
	while (to_fill > 0) {
		stream_playback->push_frame(Vector2(buffer[index], buffer[index + 1]));
		index = index + 2;
		to_fill = to_fill - 1;
	}
}
#+end_example

** Testing Framework

GDScript/integration tests verify the GDExtension classes inside a running
Godot instance. C++ unit tests cover standalone logic that doesn't need Godot
(helper functions, data transforms).


1. **GdUnit4** (GDScript/GDExtension) — tests that run inside Godot.
   Downloaded and installed by ~scripts/install_addons.sh~.
   CI runs via MikeSchulze/gdUnit4-action@v5.


*** Doctest for C++ tests
**Doctest** (C++) — header-only unit test framework for standalone C++ logic.
   Add ~doctest.h~ to ~tests/~, write test files as ~tests/cpp_*.cpp~ that
   compile with a separate ~#define DOCTEST_CONFIG_IMPLEMENT~ main.

Doctest is a good fit for this project because:

- Header-only: no separate build/link of a test framework
- Fast compilation: important for a GDExtension that rebuilds frequently
- Minimal setup: drop ~doctest.h~ in ~tests/~, write test files with
  ~DOCTEST_CONFIG_IMPLEMENT~ in exactly one translation unit
- Standalone: tests can compile and run without Godot for pure logic

Usage sketch:
#+begin_src cpp :tangle no
// tests/cpp_sfloader.cpp
#define DOCTEST_CONFIG_IMPLEMENT
#include "doctest.h"
#include <cstring>

extern int position;
extern long fsize;
extern void *my_open(const char *);
extern int my_read(void *, long long, void *);
extern int my_seek(void *, long long, int);

TEST_CASE("my_open parses &%p encoded pointer") {
    int x = 42;
    char buf[64];
    snprintf(buf, sizeof(buf), "&%p", &x);
    void *result = my_open(buf);
    CHECK(result == &x);
}

TEST_CASE("my_seek rejects out-of-bounds") {
    position = 0;
    fsize = 100;
    CHECK(my_seek(nullptr, -1, SEEK_SET) == FLUID_FAILED);
    CHECK(my_seek(nullptr, 101, SEEK_SET) == FLUID_FAILED);
}

TEST_CASE("my_read advances position") {
    position = 0;
    fsize = 10;
    char src[10] = "abcdefghi";
    char dst[10] = {};
    CHECK(my_read(dst, 3, src) == FLUID_OK);
    CHECK(position == 3);
    CHECK(dst[0] == 'a');
    CHECK(dst[2] == 'c');
}
#+end_src
** Addons management

- Third-party addons (gdUnit4) are NOT tracked in git.
  ~addons/*~ is gitignored; ~!addons/midi/~ exception keeps the project's own
  addon tracked.
- ~scripts/install_addons.sh~ downloads gdUnit4 archive from GitHub and
  extracts ~addons/gdUnit4/~.
- CI runs the install script before building, then runs tests after build.
- Local dev: run ~scripts/install_addons.sh~ after clone, then
  ~godot --headless --addon gdUnit4~.
