godot-gdnative-fluidsynth
=========================

Godot gdnative fluidsynth library to allow playing music using fluidsynth. Provides some primitives like ~AudioStreamMidiTrack~ and ~EventStreamMidiTrack~.

## Contents
,* godot-cpp as a submodule (`godot-cpp/`)
,* GitHub Issues template (`.github/ISSUE_TEMPLATE.yml`)
,* GitHub CI/CD workflows to publish your library packages when creating a release (`.github/workflows/builds.yml`)
,* preconfigured source files for C++ development of the GDExtension (`src/`)
,* setup to automatically generate `.xml` files in a `doc_classes/` directory to be parsed by Godot as [GDExtension built-in documentation](https://docs.godotengine.org/en/stable/tutorials/scripting/gdextension/gdextension_docs_system.html)


### Configuring an IDE
You can develop your own extension with any text editor and by invoking scons on the command line, but if you want to work with an IDE (Integrated Development Environment), you can use a compilation database file called `compile_commands.json`. Most IDEs should automatically identify this file, and self-configure appropriately.
To generate the database file, you can run one of the following commands in the project root directory:
```shell
# Generate compile_commands.json while compiling
scons compiledb=yes

# Generate compile_commands.json without compiling
scons compiledb=yes compile_commands.json
```

## Usage - Actions

This repository comes with a GitHub action that builds the GDExtension for cross-platform use. It triggers automatically for each pushed change. You can find and edit it in [builds.yml](.github/workflows/builds.yml).
After a workflow run is complete, you can find the file `godot-cpp-template.zip` on the `Actions` tab on GitHub.

*** Architecture

**** Source Files (src/)
| File                     | Purpose                                               |
|--------------------------+-------------------------------------------------------|
| register_types.cpp       | GDExtension entry point, registers all classes        |
| gdmidiplayer.cpp/h       | Main GDMidiAudioStreamPlayer class wrapping FluidSynth|
| midi_file_reader.cpp/h   | Resource loader for MIDI files                        |
| soundfont_file_reader.cpp/h | Resource loader for SoundFont files               |

**** Key Integration Pattern

FluidSynth expects file paths, but Godot resources are in-memory. The extension uses a custom sfloader with memory callbacks (~my_open~, ~my_read~, ~my_seek~, ~my_tell~, ~my_close~) that interpret a pointer address encoded as a string (~"&%p"~) to load soundfonts from Godot's resource system.

**** Build Output
- ~bin/<platform>/~ - Raw build output
- ~gdmidiplayer/bin/<platform>/~ - Copied for Godot project use

Android requires cross-compiling fluidsynth with the Android NDK.

******* Prerequisites

- Android NDK (r21 or later recommended)
- CMake 3.13+
- Fluidsynth source code

******* Build Steps

1. Set up NDK toolchain:
   #+begin_src shell :tangle no
   export ANDROID_NDK=/path/to/android-ndk
   export TOOLCHAIN=$ANDROID_NDK/toolchains/llvm/prebuilt/linux-x86_64
   #+end_src

2. Build fluidsynth for each ABI (arm64-v8a, armeabi-v7a, x86, x86_64):
   #+begin_src shell :tangle no
   # Example for arm64-v8a
   mkdir build-android-arm64 && cd build-android-arm64
   cmake .. \
     -DCMAKE_TOOLCHAIN_FILE=$ANDROID_NDK/build/cmake/android.toolchain.cmake \
     -DANDROID_ABI=arm64-v8a \
     -DANDROID_PLATFORM=android-21 \
     -DBUILD_SHARED_LIBS=OFF \
     -Denable-floats=ON \
     -Denable-threads=ON \
     -Denable-openmp=OFF \
     -Denable-alsa=OFF \
     -Denable-jack=OFF \
     -Denable-pulseaudio=OFF \
     -Denable-pipewire=OFF \
     -Denable-oss=OFF \
     -Denable-readline=OFF
   cmake --build .
   #+end_src

3. Copy static library and headers to a known location for SConstruct.

****** Root Cause Analysis

The linker finds the 64-bit ~libfluidsynth.so~ but skips it because it's
incompatible with the 32-bit target. The workflow installs ~gcc-multilib~ and
~g++-multilib~ for cross-compilation toolchains, but does not install the 32-bit
fluidsynth library (~libfluidsynth-dev:i386~).

Ubuntu uses multiarch: 32-bit libraries install to ~/usr/lib/i386-linux-gnu/~
while 64-bit goes to ~/usr/lib/x86_64-linux-gnu/~. The ~pkg-config~ call in
SConstruct returns 64-bit paths regardless of target architecture.

****** Solution Options

******* Option A: Install 32-bit fluidsynth via multiarch (Recommended)

Pros:
- Native package manager integration
- Automatic dependency resolution
- Matches the 64-bit approach

Cons:
- Requires enabling i386 architecture on GitHub runners
- May have dependency conflicts with 64-bit packages
- Ubuntu 22.04 runners may not have ~libfluidsynth-dev:i386~ readily available

Implementation:
#+begin_src yaml :tangle no
- name: Linux - Install 32-bit fluidsynth
  if: ${{ matrix.target.platform == 'linux' && matrix.target.arch == 'x86_32' }}
  run: |
    sudo dpkg --add-architecture i386
    sudo apt-get update
    sudo apt-get install -y libfluidsynth-dev:i386 pkg-config:i386
#+end_src

SConstruct would need modification to use ~pkg-config~ with ~PKG_CONFIG_PATH~
pointing to 32-bit libraries:
#+begin_src python :tangle no
if platform == "linux" and arch == "x86_32":
    env["ENV"]["PKG_CONFIG_PATH"] = "/usr/lib/i386-linux-gnu/pkgconfig"
#+end_src

******* Option B: Cross-compile fluidsynth from source

Pros:
- Full control over build configuration
- Works even if 32-bit packages unavailable
- Can optimize for specific use case

Cons:
- Significantly increases CI build time
- Must also cross-compile fluidsynth's dependencies (glib, etc.)
- Complex CMake cross-compilation setup
- Maintenance burden

Implementation would require a separate job to build fluidsynth:
#+begin_src yaml :tangle no
- name: Build fluidsynth for i386
  run: |
    git clone --depth 1 https://github.com/FluidSynth/fluidsynth.git
    cd fluidsynth
    mkdir build && cd build
    cmake .. \
      -DCMAKE_C_FLAGS="-m32" \
      -DCMAKE_CXX_FLAGS="-m32" \
      -DCMAKE_INSTALL_PREFIX=${{ github.workspace }}/fluidsynth-i386 \
      -DBUILD_SHARED_LIBS=OFF \
      -Denable-readline=OFF \
      -Denable-dbus=OFF
    make -j$(nproc)
    make install
#+end_src

******* Option C: Skip 32-bit Linux builds (Pragmatic)

Pros:
- Zero additional complexity
- 32-bit Linux usage is extremely rare in 2025+
- Godot itself barely supports 32-bit Linux (deprecated)
- Allows focus on platforms users actually need

Cons:
- Incomplete platform coverage
- May disappoint edge-case users

Implementation: Remove ~x86_32~ from Linux targets in workflow matrix:
#+begin_src yaml :tangle no
target:
  [
    { platform: linux, arch: x86_64, os: ubuntu-22.04 },
    # { platform: linux, arch: x86_32, os: ubuntu-22.04 },  # Removed
    { platform: linux, arch: arm64, os: ubuntu-22.04-arm },
    { platform: linux, arch: arm32, os: ubuntu-22.04-arm },
    # ...
  ]
#+end_src

******* Option D: Use Docker container with 32-bit environment

Pros:
- Completely isolated 32-bit environment
- No multiarch conflicts
- Reproducible builds

Cons:
- Adds Docker complexity to workflow
- Slower than native builds
- Requires maintaining a container image

Implementation:
#+begin_src yaml :tangle no
- name: Build 32-bit Linux in container
  if: ${{ matrix.target.arch == 'x86_32' }}
  uses: docker://i386/ubuntu:22.04
  with:
    args: |
      apt-get update && apt-get install -y libfluidsynth-dev scons
      scons platform=linux arch=x86_32
#+end_src

****** Recommendation

**Option C (Skip 32-bit Linux)** is the most pragmatic choice:
- Godot 4.x has effectively deprecated 32-bit Linux support
- The effort to maintain 32-bit builds exceeds their utility
- Users requiring 32-bit can build from source locally

If 32-bit support is required, **Option A** is the cleanest approach, but
requires testing whether ~libfluidsynth-dev:i386~ is available and whether
pkg-config correctly resolves 32-bit paths.

****** Root Cause Analysis

These are C++ standards compliance errors. The code uses GCC/Clang extensions
that MSVC (and strict C++ mode) rejects:

******* Error 1: ~void *~ arithmetic (line 18)

#+begin_src cpp :tangle no
memcpy(buf, (handle + position), count);  // handle is void*
#+end_src

In standard C++, ~void*~ has no size, so pointer arithmetic is undefined.
GCC/Clang allow this as an extension (treating ~void*~ like ~char*~), but
MSVC strictly follows the standard and rejects it.

******* Error 2: Variable-Length Array (line 159)

#+begin_src cpp :tangle no
char midi_file[byte_array.size()];  // VLA - not allowed in C++
#+end_src

Variable-Length Arrays (VLAs) are a C99 feature. They're not part of any C++
standard. GCC/Clang support them as an extension, but MSVC does not.

******* Error 3: Array assignment (line 162)

#+begin_src cpp :tangle no
midi_file[i] = byte_array[i];  // This error is a cascade from the VLA issue
#+end_src

This error occurs because MSVC interprets ~midi_file~ as a function-like entity
due to the failed VLA parse, not because the assignment itself is invalid.

****** Solution Options

******* Option A: Fix code for C++ standards compliance (Recommended)

This is the correct long-term solution. All three issues have straightforward fixes:

*Fix for void* arithmetic* (line 18):

// After - cast to char* for byte-level arithmetic:
memcpy(buf, (static_cast<char*>(handle) + position), count);

// Or use uint8_t* for clarity:

#+end_src
